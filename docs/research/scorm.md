# Research: scorm

_Source: workflow agent `research:scorm`._

## Summary

SCORM 1.2 is the right target for a single-SCO Vite/Three.js game in D2L Brightspace: the package is a zip with imsmanifest.xml at the root, one <organization>/<item> pointing at one <resource adlcp:scormtype="sco" href="index.html">, an optional <adlcp:masteryscore> on the item, and (per the 1EdTech packaging rule) the referenced XSD control files at the package root. At run time the page must locate window.API by walking window.parent (ADL sample stops after 7 levels; pipwerks after 500) and then window.opener, call LMSInitialize(""), write cmi.core.score.min/max/raw (0-100), cmi.core.lesson_status, cmi.suspend_data (hard 4096-char cap in 1.2), cmi.core.lesson_location (255 chars), cmi.core.exit, then LMSCommit("") and LMSFinish(""). In D2L the instructor uploads via Content > Upload/Create > New SCORM/xAPI Object (Content Service, the "new SCORM player"); at upload they answer Yes to "create a grade item" and pick a grade calculation method (Highest Attempt is default), and choose embedded player vs new window. Only cmi.core.score.raw reaches the D2L gradebook, so the game must always report a numeric raw score, not just a status. The legacy engine (Course Admin > Import/Export/Copy Components) only supports "latest attempt" grading, marks topics complete on visit, and is not reported in Data Hub. The Content Service serves package files from content.<region>.content-service.brightspace.com, a different origin from the LMS host, which is exactly why content must find the API in its own frame/opener chain and must wrap every cross-window property access in try/catch. Recommended design: a small ScormAdapter that runs in "LMS mode" when an API is found and "standalone mode" (localStorage, same serialized state) otherwise; score = percent of challenge points earned (0-100, monotonic within an attempt), masteryscore in the manifest equal to the course pass mark, suspend_data as a compact versioned bitmask kept under ~3500 chars, commit on every milestone and on visibilitychange/pagehide, and LMSFinish once on pagehide or an explicit "Save & Exit" button. Caveat: every D2L-specific UI/behaviour claim below comes from search snippets of D2L Community/university KB pages because community.d2l.com, documentation.brightspace.com and d2l.com were blocked by the egress proxy; they are marked "likely", not "verified".

## Recommendations

- Target SCORM 1.2, single SCO. Package = dist/ output plus imsmanifest.xml at the zip ROOT (no wrapping folder), plus the three XSDs (imscp_rootv1p1p2.xsd, adlcp_rootv1p2.xsd, imsmd_rootv1p2p1.xsd) and ims_xml.xsd at the root. Add a `scripts/build-scorm.ts` (or shell) step that runs `vite build`, generates the manifest by globbing dist/** into <file href="..."/> entries (index.html first, forward slashes, no leading ./), copies the XSDs, and zips with `zip -r ../orgocraft-scorm12.zip .` from inside dist/. Use the pipwerks manifest verbatim with: identifier="orgocraft", organization title "OrgoCraft: Organic Chemistry", <item identifier="item_1" identifierref="res_1"><title>OrgoCraft</title><adlcp:masteryscore>70</adlcp:masteryscore></item> (set to whatever pass mark the instructor wants), and <resource identifier="res_1" type="webcontent" adlcp:scormtype="sco" href="index.html">.
- Implement `src/scorm/ScormAdapter.ts` with discovery that (a) walks `win = window; for (i=0;i<10;i++){ try { if (win.API) return win.API; } catch {} if (win.parent === win) break; win = win.parent; }` and then repeats the same walk from `window.opener` (and `window.top.opener`), wrapping every access in try/catch so a cross-origin SecurityError (guaranteed possible in D2L's Content Service, which serves content from content.<region>.content-service.brightspace.com) simply ends the walk instead of crashing the game. Never use document.domain. If nothing is found within ~2 s of load, switch to standalone mode.
- LMS-mode call sequence: on load `LMSInitialize("")`; read `cmi.core.lesson_status`, `cmi.core.entry`, `cmi.suspend_data`, `cmi.core.lesson_location`; then immediately `LMSSetValue("cmi.core.score.min","0")`, `LMSSetValue("cmi.core.score.max","100")` and, if status is 'not attempted', set `cmi.core.lesson_status` = 'incomplete'; `LMSCommit("")`. On every challenge completion: set `cmi.core.score.raw` (integer string 0-100), set `cmi.core.lesson_location` (current area/challenge id, <=255 chars), set `cmi.suspend_data`, set lesson_status 'passed' when raw >= mastery (or 'completed' if the instructor chose not to grade pass/fail), and `LMSCommit("")`. Do not write score.raw until it is >0 so students who merely open the game do not get a 0 recorded under a 'Last Attempt'/'First Attempt' calculation. Throttle non-milestone commits to one per ~30 s.
- Exit handling: register `document.addEventListener('visibilitychange', ...)` to `LMSCommit("")` whenever visibilityState becomes 'hidden', and `window.addEventListener('pagehide', ...)` to set `cmi.core.exit` ('suspend' if not yet passed, 'logout' if passed), `LMSCommit("")`, then `LMSFinish("")` exactly once (guard with a `finished` flag; later calls are no-ops). Do not rely on beforeunload (unreliable on mobile, breaks bfcache). Also provide an explicit 'Save & Exit' button that does the same sequence and then, in new-window mode, `window.close()` -- D2L users who just close the popup otherwise start a new attempt. Always commit before finish; do not depend on the LMS committing implicitly.
- Score model: define a fixed roster of N challenges, each with a point weight (e.g., easy 1, medium 2, boss 4). raw = round(100 * earnedPoints / totalPoints). Make it monotonic within an attempt (never lower a previously reported raw) so partial progress is never overwritten by a lower value. Put the pass mark in the manifest masteryscore AND enforce it in code by writing 'passed'/'failed' yourself (the LMS may or may not override from masteryscore). Keep the grade item's points at 100 in D2L (the instructor edits 'Grade Out Of'/Max Points to 100) so raw maps 1:1 to the gradebook percentage.
- suspend_data format: a versioned, compact string, e.g. `v1|<base64 bitmask of completed challenge ids>|<current area id>|<seed>`; no JSON key names, no player position/inventory beyond what is needed to resume. Assert length <= 3500 chars in a unit test (hard limit 4096 in SCORM 1.2; D2L will not raise it). Persist the same string to localStorage in both modes so a student can recover if the LMS drops suspend data (new-player resume bugs are reported). If the design later needs more state, switch to a SCORM 2004 4th Edition manifest (64,000-char suspend_data, API_1484_11, completion_status + success_status, score.scaled) rather than trying to compress past 4096.
- Standalone mode (no API found, e.g. served from D2L Manage Files as plain HTML, or opened at localhost): identical game logic, state written to `localStorage['orgocraft.v1']`, an unobtrusive HUD badge 'Progress saved locally - not connected to the gradebook'. In LMS mode show 'Connected to course gradebook'. Never block play on API failure; log LMSGetLastError()/LMSGetErrorString() to console when a call returns 'false'.
- Instructor steps to document for D2L (new player): Content > module > Upload/Create > New SCORM/xAPI Object > Upload the zip > in the dialog choose 'Yes' to create a grade item, Grade Calculation Method = Highest Attempt (best fit for a game students may replay), Course Package Player Options = 'Open player in new window' (a fullscreen WebGL canvas is cramped in the embedded iframe and D2L's own troubleshooting article lists 'SCORM too small/too large' as a top issue) > Save. Afterwards, in Grades > Manage Grades, set the item to 100 points and put it in a category. Tell them NOT to use Course Admin > Import/Export/Copy Components (legacy player: 'latest' grade only, complete-on-visit, no Data Hub reporting). Tell them to test resume/grades with a real test-student account, not 'View as Learner'.
- Also offer the plain-upload path for instructors who do not need a grade: upload dist/ contents into Manage Files and link index.html as a Content topic; the game runs in standalone mode. The existing base './' config already supports this.
- Testing plan before handing over: (1) unit-test the adapter against a fake `window.API` (scorm-again's test harness pattern, or a 20-line stub that records SetValue calls); (2) run the zip through a free SCORM Cloud account (Rustici) which shows every API call and flags manifest errors; (3) in a D2L sandbox test both embedded and new-window modes, in Chrome with third-party cookies blocked and in Safari, and confirm the grade appears under Highest Attempt after a second attempt with a lower score.

## Risks

- All D2L UI/behaviour statements (menu labels, grade calculation options, embedded vs new window, only score.raw reaching the gradebook, completion-threshold rule, 2 GB limit) come from search-result snippets of D2L Community and university KB pages because community.d2l.com, documentation.brightspace.com, d2l.com and the university mirrors were egress-blocked; labels may differ slightly in the instructor's D2L version and should be checked against the live course shell.
- The exact frame/opener layout of D2L's Content Service player was not verifiable. If D2L exposes the API only in a frame that is not same-origin with the content (or only via a postMessage bridge), plain window.parent discovery would silently fail; the adapter must degrade to standalone mode and the instructor should run a real end-to-end test before grading anything.
- Whether D2L applies the manifest masteryscore to override lesson_status is undocumented in reachable sources; the game must set passed/failed itself and must always emit a numeric score.raw, otherwise nothing lands in the gradebook.
- SCORM 1.2 suspend_data is capped at 4096 characters and D2L states it cannot raise it; a voxel world's state must be reduced to a compact challenge bitmask, or the project must move to SCORM 2004 4th Edition.
- New-window launch depends on popups being allowed and on third-party cookies for the content-service origin; embedded launch constrains the WebGL canvas size and may show D2L's known 'too small/too large' problem. Either mode can be affected by learners opening the topic in multiple tabs (each may be its own attempt).
- Multiple reports say the new SCORM player's resume/bookmark does not always restore suspend data and can reset visible progress to 0% on revisit; keeping a localStorage mirror mitigates lost progress but not gradebook effects, so 'Highest Attempt' should be the recommended calculation method.
- beforeunload/pagehide are best-effort; a hard browser kill on mobile or a crashed WebGL context can skip the final LMSFinish. Frequent LMSCommit on milestones is the only real protection.
- The 1EdTech rule that referenced XSDs sit at the package root is spec text; whether D2L's importer enforces it was not verifiable, so the safe path is to include them.
